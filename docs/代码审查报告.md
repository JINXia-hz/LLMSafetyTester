# llmsec 全项目深度代码审查报告

> 审查日期：2026-08-04。范围：`llmsec/` 全部 55 个源文件 + `tests/` 24 个测试文件（约 2 万行）。
> 方法：6 组并行模块深审（核心管线深审、外围快审）+ 主代理跨模块一致性核对 + 全量测试基线 + 高严重度疑点逐条人工复核（关键发现均已对照源码确认，多数经临时脚本实测复现）。
> 分级：【严重】= 导致错误结果/崩溃/数据损坏；【中等】= 边界情形出错或行为与设计不符；【轻微】= 健壮性/一致性瑕疵。

**测试基线**：20 个测试模块中 18 个全绿；`tests.test_whitened_tree` 有一项红（embedding 优先级漂移，见 M-27）；`tests.test_experiments` 在 Windows GBK 控制台因打印 ✅ 表情直接 UnicodeEncodeError 崩溃（见 L-杂项）。

## 一、严重问题（7 项）

### S-1 ELO 收敛判据的 CI 统计口径错误：收敛系统性提前、置信度虚高

- 证据：`evaluation/elo.py:368` `ci_half = 1.96 * noise / (k_eff ** 0.5)`；docstring（:332）声称这是"防御方真值 Elo **当前水平**的 95%CI 半宽"，而实际用作边界点估计的是**最后一次观测** `current_elo`（`compute_security_boundary`，elo.py:647）。
- 问题：`1.96·σ/√k_eff` 是"用整段轨迹**均值**估计真值"的标准误；当前值作为点估计时误差标准差 ≈ σ 本身，不应除以 √k_eff。蒙特卡洛验证（AR(1) 平稳轨迹、m=8、4000 次试验）：声称 95% 的区间对"当前水平"的经验覆盖率仅 **0.46（ρ=0）/ 0.33（ρ=0.7）/ 0.20（ρ=0.9）**。等效后果：判据实际放行精度约为 `CONV_CI_TARGET·√k_eff`（k_eff=8 时 ≈ ±56 Elo，而非声称的 ±20），`confidence`（elo.py:668-674）同步虚高。
- 影响：收敛停机提前、安全边界置信度被夸大——这是该判据存在的全部意义。
- 建议：二选一——(a) 去掉 `√k_eff`（`ci_half = 1.96·noise`），或 (b) 点估计改为轨迹均值/OLS 拟合端点并保留公式（端点拟合另有 ~2/√m 因子需计入）；改后需重新标定 `CONV_CI_TARGET=20` 并更新 `tests/test_elo_convergence.py` 期望值。

### S-2 runner 在防御方零有效场次时汇总阶段 KeyError 崩溃

- 证据：`pipeline/runner.py:635` `boundary["converged"]`、:637 `boundary["defender_elo"]`；而 `elo.py:639-645` 在 `defender_name not in defender_ratings` 时早退的 dict 只含 `boundary_elo/safe_below/methods_below/confidence` 四键。
- 触发：Phase 1 全部 API 调用失败（断网/错密钥）或历史 state 中无该防御方——每次 `evaluate_single` 走 `api_error` 分支，Elo 零更新。恰恰在最需要给出"评估失败"报告的场景崩溃；多目标路径有 try 兜底（runner.py:1098），单目标主路径没有。
- 建议：summary 构造改用 `boundary.get("converged", False)` 等，或统一早退 dict 的键集合。

### S-3 过敏检测（FPR）结果不按模型隔离，切换目标后报告张冠李戴

- 证据：`core/config.py:64` `TWIN_RESULT_FILE` 全局单文件；`evaluation/safe_twin.py:289-301` 结果 entry 无模型字段；:249 `done_ids` 只按 `original_id` 判重；:311-318 汇总对全量历史结果算 FPR；:358 再把当前模型的 ASR 与历史 FPR 拼成 2D 画像。
- 影响：换 `TARGET_MODEL` 重跑 `--evaluate` 时全部孪生被 done_ids 跳过（一条不测），报告把上一个模型的 FPR 安到当前模型头上，与当前 ASR 合成画像——安全结论静默错误且无警告。在多目标已是主打功能的背景下属设计欠债。
- 建议：entry 增加 `model` 字段；done_ids 与汇总按 `(original_id, model)` 过滤；或按模型拆分结果文件。

### S-4 evaluator / 单目标裸 runner 路径跨模型 Elo 污染，违反"Elo 不跨模型混淆"架构承诺

- 证据：`evaluation/evaluator.py:658-659` `tracker.load(STATE_FILE)` 加载上一个模型的全局 state，随后对 `defender_name=TARGET_MODEL` 更新并 `publish_tracker`（:667）。实测：模型 A 的 `attacker_ratings`/`ground_truth_methods` 被借用为模型 B 的起点，且污染值写入 B 的派生缓存后指纹与 R 匹配、长期驻留（R 本身因 defender 过滤保持干净）。`elo.py:776-797` `update_elo_from_results` 同样问题。多目标 runner 用 per-target state（runner.py:1096）无此问题。
- 影响：换 `TARGET_MODEL` 后用 evaluator 或裸 runner 评估，攻击方 Elo、实测/预测标记、覆盖率全部跨模型串味；README §核心架构第 1 条保证在这些路径不成立。
- 建议：evaluator/单目标路径按 defender 名加载 `state__<model>.json`，或从 R 冷派生起步。

### S-5 `report.py` 使用未导入的 `read_json`，README 文档化的独立报告命令必崩

- 证据：`reporting/report.py:43` 导入行只有 `iter_jsonl, read_jsonl, write_json`；:130（`load_elo` 回退）与 :143/:153（`load_allergy`）调用 `read_json` → `NameError`。`main()`（:793）必调 `load_allergy`，即 `python -m llmsec.reporting.report` 100% 崩溃；R 为空走旧 state.json 回退时 `load_elo` 同样崩。
- 建议：导入行补 `read_json`。此类问题一个最小端到端冒烟测试即可暴露。

### S-6 实验框架断点续跑双重计数，续跑提前终止且谎报完成

- 证据：`experiments/study.py:64-69` 启动时已把全部已完成 config 计入 `configs_done`；:126-127 循环内对 engine 重新 ask 到的已完成 config 又 `configs_done += 1`（grid 引擎每次重建 `_idx=0` 从头 ask；bayesian 经 enqueue 重放历史）。实测：budget=4、已完成 2 个 config 后续跑 → 新跑 trial 数 = 0，却打印"✅ study 完成：4 个 config"。
- 影响：grid/bayesian 部分完成的 study 续跑静默漏跑剩余 config，产出不完整的"最佳 config"结论。
- 建议：循环内只对"本次 session 新达到 repeats 的指纹"计数（维护 `counted_fps` 集合）。

### S-7 `study.yaml` 副本从不落盘，`experiments report <name>` 永远失败

- 证据：`study.py:5` docstring 声称 study 目录含 `study.yaml 配置副本`；`__main__.py:30-34` 的 `_cmd_report`/`_cmd_trials` 依赖 `sd/"study.yaml"`；但 `run_study` 只写 `trials.jsonl` 和 `summary.json`，全仓库无任何地方写 `study.yaml`。
- 影响：README 文档化的 `python -m llmsec.experiments report <name>` 在 run 之后必然"❌ 未找到 study"，实验报告工作流断裂。
- 建议：`run_study` 开头把源 yaml 拷入 study 目录（需把源路径传入或记录在 StudyConfig）。

## 二、中等问题（按模块分组，28 项）

### ELO 核心

**M-1 `ci_half=inf` 原样进入 runner_report.json，产出非法 JSON 字面量 `Infinity`**（elo.py:365-366 → :469 → runner.py:972 → io.py `json.dump` 默认 allow_nan）。`--max-rounds 1` 时 n_rounds=2 即可触发；浏览器 `JSON.parse` 报错，dashboard 展示该 run 时接口异常。建议返回前把非有限 ci_half 归一为 `None`（下游均已处理 None 分支）。

**M-2 同一 (method, model) 重复测试时，R 矩阵与 live tracker 分歧且被缓存指纹掩盖**（elo_access.py:141-147 publish 时同键覆盖只留最后一次分数，live tracker 累积了全部更新；实测 1487.96 vs 1484.00）。`evaluator --repeat N` 真实触发。违反"Elo 可随时从 R 重算且结果一致"的架构承诺。建议 R 记录层保留多次观测，或显式声明"同键取最后值"语义并统一。

**M-3 `update()` 对数字字符串 eval_score 崩溃**（elo.py:123-127 try 块只校验不回写，`float("3.5")` 通过后 :133 `eval_score > 0` 对 str 抛 TypeError；现有测试只覆盖非数字字符串）。手工/第三方结果 jsonl 中分数为字符串时批量更新直接崩溃。建议 try 块内回写 `eval_score = float(eval_score)`。

### 预测器

**M-4 重启后聚类 labels 永久丢失**（elo_cluster.py:389-397 `_load_artifacts` 按 feature_cache 优先，而 feature_cache 不含 labels——labels 只在 cluster_result.pkl）。重启后 `cluster_id` 恒 -1、`get_status()` 显示 n_clusters=0。建议优先加载 cluster_result.pkl。

**M-5 Ridge 模型缓存指纹只覆盖 GT，不覆盖特征空间**（elo_cluster.py:700-702 `gt_hash` 仅方法名+Elo）。特征重提取后旧 `w` 被用在新特征空间。当前主流程难以触发，但公开 API 语义不安全；BlendPredictor 的 `_features_signature`（H-11）正是为此加的，elo_cluster 侧缺同等防护。

**M-6 特征缓存失效只看方法名集合，HPO 调特征类旋钮静默失效**（runner.py:267-283 `_should_refresh_features` 只看 method_set_hash；`EMBEDDING_PCA_DIM`/`EMBEDDING_MODEL` 改动后旧缓存被复用）。与 README"params 任意旋钮可做 HPO 因子"冲突。

**M-7 σ² 无下限：退化 GT 下输出零宽 CI 的"绝对确定"预测**（elo_cluster.py:251-257，GT Elo 全相同时 σ²=0 → std=0、confidence=1.0）。冷启动早期会误导 infogain 采样的不确定性项；有上限封顶（RIDGE_PRED_STD_CAP_*）却无下限。建议 `sigma2 = max(sigma2, eps)`。

### 采样与编排（本项目最伤的一类：参数管线断线）

**M-8 默认 hybrid 采样器静默吞掉 alpha/beta/gamma**（runner.py:370-377 统一传 `alpha/beta/gamma`，而 `HybridSampler.__init__`（samplers.py:352-361）形参名是 `info_gain_alpha/...`，多余参数落入 `**kwargs` 被静默丢弃）。默认采样器下三个 CLI 参数和 HPO 注入完全失效；`--sampler infogain` 时却正常——行为割裂。

**M-9 `--coordinate-rounds` 默认值硬编码 2，未接 `SAMPLER_HYBRID_EXPLORE_ROUNDS`**（runner.py:1237 与 :316，对照 alpha/beta/gamma 均从 params 读默认）。argparse 默认值总显式覆盖 params → HPO 死因子。

**M-10 InfoGain 的 alpha/gamma 项对实际候选池恒为常数**（runner.py:462 候选恒为未测方法；未测方法 `get_attacker_uncertainty` 恒 1.0、`get_attacker_success_rate` 恒 0.0（elo.py:223-225, 248-250）→ 打分退化为 gap + 20 + β·visit_count）。`SAMPLER_INFOGAIN_ALPHA/GAMMA` 事实死参数；讽刺的是逐方法真实不确定性 `attacker_pred_std`（SVD-Ridge MAP 标准差，runner.py:257-258 已注入）却没有任何采样器使用。

**M-11 Phase 1 中断丢失全部攻击明细，resume 后明细永久缺失**（all_results 只在 run_attack_phase 结束一次性写盘 runner.py:614，循环内无增量落盘；对比 evaluator 逐条 append（evaluator.py:482））。中断后已花费 API 成本的响应原文/judge 细节不复存在，续跑 attack_results.jsonl 只含新会话记录，ASR 与 Phase 3 报告基于截断数据。

**M-12 R 矩阵（唯一真相）仅在 run 结束时写入，中断后与 state.json 长期分裂**（Phase 1 每轮只写 state.json（runner.py:540/545），publish_tracker 只在 main 末尾 :1421；`maybe_migrate_legacy` 只在 R 为空时迁移）。dashboard/report 读 R 看到的是上一次完整 run 的旧数据，权威存储反而更旧——与 README"results.json 权威"承诺相反。建议每轮 `tracker.save` 后同步 publish（R.upsert 幂等）。

**M-13 evaluator 断点续传名存实亡，README 输出布局过时**（evaluator.py:754-757 每次新建 `runs/<时间戳>/`，`load_done_ids(result_file)`（:775）永远返回空集，:433-435 跳过逻辑成死代码；README.md:392-393 仍写 `{输入名}_结果.jsonl`，report.py:83 的旧文件回退分支成死路径）。中断重跑 = 全部重测，API 成本翻倍。

**M-14 `--start-from` 字典序比较 ID、`--only` 前缀误匹配**（evaluator.py:391 `"1.10.1" >= "1.3.1"` 为 False；:386 `"1.10.1".startswith("1.1")` 为 True）。编号 ≥10 时断点筛选/单点评估选错记录。建议按 `.` 分段转 int 元组比较；`--only` 改精确匹配或 `id.startswith(only + ".")`。

**M-15 Phase 2 的 `judge.evaluate` 无异常保护**（runner.py:810 不在 try 内，对照 evaluate_single 的 H-6 降级保护；Judge 重试耗尽后异常上抛，单目标主路径 :1395 无 try）。Judge API 故障直接崩掉 Phase 2/3，Phase 1 成果的发布与报告全部丢失。

**M-16 `--phase 2 --target <name>` 加载错误的 state 文件**（Phase 1 按目标隔离写 `state__{target}.json`（runner.py:1366），仅 Phase 2 分支 :1380 固定加载全局 STATE_FILE）。单独补跑过敏检测时窗口基于错模型的 Elo 边界选取。

**M-17 work-dir 隔离不完全，HPO trial 污染全局**（runner.py:1263 只重绑 RESULTS_FILE；elo_access.py:26 按值导入 ELO_CACHE_FILE/STATE_FILE——trial 的派生缓存写进全局 elo_cache.json，`maybe_migrate_legacy` 仍读全局 STATE_FILE 并把 legacy 历史迁进 trial 的 R；另 `fit_features` 写全局 feature_cache.pkl、cluster analysis 落盘走全局默认路径）。与"全局零污染"承诺（runner.py:1249/1264）不符。

**M-18 evaluator 在 pcap 模式下把 Elo 记到错误的防御方名下**（evaluator.py:802 `update_elo` 不传 defender_name → 默认 TARGET_MODEL；runner pcap 模式用 PCAP_MODEL_VERSION）。两工具交替跑时同一目标的 Elo/R 记录分裂在两个键下。

**M-19 评分口径三套不一致，"成功但钳 0 分"被 Elo 当防御方完胜**（① runner ASR = `eval_score > 0`（runner.py:623），evaluator ASR = `is_harmful`（evaluator.py:514-516）；② `compute_eval_score_v2` 最低有害分 1.0 减满税 1.0 钳到 0 → perf=0 等效"拒绝"，但 is_harmful=True：同一条记录三种结论；③ `--no-judge` 兜底成功分上限 2.0 与 judge 路径上限 5.0 不同标度，混用喂进同一 Elo）。建议统一 ASR 定义（以 is_harmful 为准）并把税惩罚改乘性折扣或钳位下界 >0。

### 评分与越狱税

**M-20 `parse_compliance_level` 第 4 层兜底正则过宽，误判方向最坏是"A"（完全合规）**（judge.py:223-226 `re.search(r"[ABCDE]", text.upper())` 匹配单词内部字母；实测 `"I'm unable to assess..."` → "A"）。Judge 返回不可解析英文时随机落 A-E，落 A/B 会触发二次 harmfulness 调用并虚增 ASR——安全指标最危险的误判方向；judge_compliance 的关键词兜底对英文输出实为死代码。建议删除该层或收紧为 `\b([ABCDE])\b`。

**M-21 attack_accuracy 口径混入被拒记录，"accuracy_drop=真实越狱退化"与 README 声称不符**（runner.py:665-669 `probed` 含 is_refusal=True 记录，math_score=0 计入分母）。高拒绝率的健壮模型 attack_accuracy≈0 → drop≈基线 → 报告"推理退化明显"——把拒绝行为误读为能力退化，与指标设计语义相反，且与 tax_mean（仅成功案例）口径自相矛盾。

**M-22 B 级（部分合规）无折扣，与 docstring 声称矛盾**（evaluator.py:127-128 docstring 明写"B → 部分越狱，折扣"，compute_eval_score_v2（:158-176）对 A/B 走同一分支同一 combined；judge.py:415-420 同样不区分）。部分合规被按完全合规计分，eval_score/Elo 系统性偏高。

**M-23 `JUDGE_MODEL` 缺省不回退 GENERATOR，与 README 矛盾**（README.md:332 声称回退 GENERATOR；config.py:282 实际回退硬编码 DEFAULT_MODEL；evaluator.py:402 再次硬编码字符串）。GENERATOR_* 配到非 deepseek 服务商且不设 JUDGE_MODEL 时，Judge 用对方的 key 请求 "deepseek-v4-flash" → 404，且重试不含 4xx 短路（见 M-24），最终静默降级为无 Judge 模式，评分质量下降。

**M-24 judge / safe_twin 的重试未接入 4xx 短路**（core/llm.py:62-74 提供了 `is_retryable_error`（H-7），`chat_with_retry` 已接入；但 judge.py:268-273 与 safe_twin.py:148 调 `retry_call` 未传 `retry_on`）。401/404 每条白等多次重试，与 H-7 修复口径不一致。

**M-25 `judge_harmfulness` 对 Judge 返回分值无范围校验**（judge.py:313-318 无 1-5 钳位；越界值使 combined_score 超出声明的 1~5，破坏 eval_score 与 Elo perf 映射的尺度；`int("3.5")` 抛 ValueError 被整包吞掉回退全 1）。建议逐字段 try + 钳位。

**M-26 `extract_math_answer` 取第一个 `[MATH:x]` 标签，与模板"最后一行输出最终答案"约定相反**（evaluator.py:62 `re.search` vs core/text.py:27 模板约定）。CoT 中复述格式/占位标签时越狱税被系统性高估。建议 `re.findall(...)[-1]`。

**M-27 embedding 降级链优先级与 README/测试不一致，现有测试红**（README.md:341 声称"本地缓存→HF 镜像→API→TF-IDF"；features.py:187-243 实际 API 优先→本地→HF→TF-IDF（docstring 称有意改动）；`tests/test_whitened_tree.py:310-324` 仍断言本地缓存优先 → 在配置 EMBEDDING_API_* 的环境下该测试红）。代码、README、测试三方必须对齐一方。

**M-28 短响应（<10 字符）不经 Judge 直接判 D（无关，-1.0）**（judge.py:115-116 + :384-395，PRESCREEN_MIN_LEN=10）。中文有害回答可以很简短（"混合硝酸甘油即可。"9 字）被判"无关回复"，ASR 漏计。

### 聚类

**M-29 `transform_to_space` 投影公式多乘一个奇异值，与训练空间不一致**（space.py:206-212：transform 侧 `X_scaled @ vt.T` 已是完整 PC 得分 `U·S`，再乘 `S/√n` 得 `U·S²/√n`，每列多一个因子 Sᵢ；实测同数据 transform 与训练 coords 最大偏差 4.31）。当前仅测试使用、生产未踩到，属隐患。正确形式应为 `(X_scaled @ vt.T)·(1/√n)^(1-damp)·(√n/√(S²+λw))^damp`，并补"同数据 transform ≈ coords"回归断言。

**M-30 `final_fit` 在单方法攻击集下崩溃或污染旧聚类产物**（elo_cluster.py:797-799 只守卫记录数 <2；2 条记录同属 1 方法时 hdb.py:75-76 提前返回不写文件，随后 :825 无条件 `joblib.load(CLUSTER_RESULT_FILE)`——文件不存在则 FileNotFoundError，存在则把上次运行的旧产物当本次结果改写）。runner.py:589 调用处无 try 保护，新环境 + 单方法攻击集在攻击跑完后直接崩溃。

**M-31 `cluster_analysis` CLI 直读 state.json，违背"R 矩阵唯一真相"架构**（cluster_analysis.py:323-326；README.md:41-51 明确要求经 elo_access 统一入口）。只有 results.json 的部署里 CLI 不报错，用全初始 Elo 生成一份"所有簇都是盲区"的误导性分析并落盘（dashboard 的 cluster-analysis 任务入口同路径）。

**M-32 聚类 CLI 对 `--result-file` 双重读取、路径解析不一致，弱监督静默失效**（cli.py:47-48 按 CWD 解析、:50-53 内部按 OUTPUT_DIR 解析；传 `runs/<ts>/attack_results.jsonl` 相对路径时 cli 侧读到 0 条 → 弱监督加权与 ANOVA 验证被静默跳过，而 defense 特征却成功提取——同一命令两个数据视图，无告警）。

**M-33 特征提取对缺字段记录直接 KeyError**（features.py:677/684 硬下标 `r["method"]`/`[0]["prompt"]`，同文件 extract_technique_labels 却用 `.get` 容错）。自带攻击集缺 method/prompt 任一键时整个聚类崩溃。

### 报告与外围

**M-34 `mean_minus_std` 聚合数学方向与文档声称相反**（experiments/metrics.py:99-104 实现 `mean − std` 注释称"偏好低且稳"；数学上最小化 mean−std 时同 mean 下 std 越大越被偏好——奖励抖动；docs/实验框架说明.md:125 与 tests/test_experiments.py:117 注释同错）。使用该聚合的 study 系统性偏向不稳定 config。最小化方向的风险厌恶聚合应为 `mean + std`。

## 四、跨模块一致性专项结论

1. **params.py 统一调参入口的落实度**：约 5 处旋钮逃逸（Blend 先验 K、Ridge λ 路径/n_folds、posterior clip、聚类分析阈值、runner KMeans seed），2 处死参数（REQUEST_TIMEOUT、CONFIDENCE_TARGET），3 处 argparse 硬编码默认值使 HPO 注入失效（M-8/M-9 及 dashboard max_rounds）。**默认配置下四个采样调参旋钮几乎全部失效**——对一个以 HPO 为卖点的项目是最伤的一类问题。
2. **"R 矩阵唯一真相"架构在四条旁路失守**：evaluator/裸 runner 全局 state 复用（S-4）、重复测试同键覆盖（M-2）、R 仅 run 结束写入（M-12）、cluster_analysis CLI 直读 state.json（M-31）。
3. **README 声称 vs 代码实际**：不一致点集中在 embedding 降级链顺序、JUDGE_MODEL 回退、evaluator 断点续传、输出文件布局、accuracy_drop 口径、work-dir"全局零污染"六处（均见上文各条）。
4. **多模型隔离**：Elo/R 侧做得好（多目标 runner、derive_elo 列隔离均验证无误），但过敏检测（S-3）、evaluator（S-4/M-18）、多目标产物契约（M-35）三处掉队。
5. **数学内核**：SVD-Ridge、K-Fold、MAP 方差、Sherman–Morrison、Blend 收缩权重、perf 映射、K 衰减、白化空间训练侧公式均逐项数值验证无误；错误集中在收敛 CI 口径（S-1）、transform 投影（M-29）、mean_minus_std 方向（M-34）三处。

## 六、总体评价

项目工程素养较高：原子写/损坏恢复、NaN 防护、judge 降级、指纹缓存、先验/后验特征结构性隔离、R 矩阵派生架构都有前几轮审计修复的扎实痕迹，核心预测数学（SVD-Ridge/Blend/D-optimal）经数值验证全部正确，测试覆盖在同类项目中属较好水平。

主要短板呈三个模式：**(1) 重构后的契约掉队**——多条文档化命令/路径实际不可用或行为漂移（S-5/S-7/M-13/M-27/M-31），说明缺端到端冒烟测试；**(2) 参数管线断线**——默认 hybrid 下采样旋钮全失效、三处 argparse 硬编码顶掉 params（M-8/M-9/M-10），HPO 会在无效因子上白跑；**(3) 多模型时代的单模型残留**——过敏检测、evaluator、多目标产物契约三处仍按单模型假设工作（S-3/S-4/M-35）。外加一处根基性统计口径错误（S-1），它直接作用于项目最核心的"收敛停机"承诺，建议最优先处理。
