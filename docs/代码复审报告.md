## 二、新引入问题（本轮修复带入）

### 【严重】

**N-S1 看板"目标模型"下拉被后端静默丢弃，新功能形同虚设**
- 证据：`app.js:988` 在 POST `/api/run/evaluate` 发送 `target`；但 `EvaluateRequest`（dashboard_api.py:871-878）无 `target` 字段，`api_run_evaluate` 拼 argv（:979-986）不带 `--target`。pydantic v2 默认 ignore extra → 不报错、静默丢弃。runner 明明支持 `--target`（runner.py:1302）。配套的 `/api/targets` 端点与下拉全部无效。（主代理已亲自核实）
- 影响：用户以为在测目标 B，实际测的是 .env 默认目标，无任何提示——评估结果张冠李戴。
- 建议：`EvaluateRequest` 加 `target: str | None`，非空时 argv 追加 `--target`（可校验在 load_targets() 已声明）。

**N-S2 evaluator 稳定结果文件无模型维度，换模型重跑直接污染 R（比原 S-3 更隐蔽）**
- 证据：M-13 修复把结果文件改为稳定路径 `OUTPUT_DIR/{base}_结果.jsonl`（evaluator.py:787），但 entry 无 `model` 字段、done_ids 不按模型过滤（:809）、汇总全量回放（:824）、S-4 的全新 tracker 把所有记录 publish 到当前 DEFENDER_NAME（:693-699）。
- 影响：换 TARGET_MODEL 重跑同一输入 → 全部记录被 done_ids 跳过（一条不测），打印的汇总是上一模型的，且他模型攻击记录被 upsert 进 R 的当前模型列——直接污染"唯一真相"R。safe_twin 的 S-3 修法（entry 加 model + 按模型过滤）应该同样应用到 evaluator。
- 建议：entry 加 `model` 字段，done_ids/all_results 按 `model==TARGET_MODEL` 过滤；或文件名带模型名。

### 【中等】

**N-M1 evaluator 用全新 tracker 覆写全局 state.json，摧毁 runner 续跑状态**（evaluator.py:694-698：S-4 修复去掉 load 但保留 `tracker.save(STATE_FILE)`）。任何一次 evaluator 运行会把 runner 长期累积的 state 替换为仅本次记录，runner 单目标 resume（runner.py:344-345）状态清零、D-optimal 重播种、收敛历史断裂。建议快照写到 run_dir 或 `state__{defender}.json`。

**N-M2 `update_elo_from_results` 同样覆写 state.json**（elo.py:815-824）：从全新 tracker 起步却 save 到全局 STATE_FILE，其它防御方 ratings/history 全丢；history 正是 maybe_migrate_legacy 迁移旧数据的唯一来源。当前无调用方，属公开 API 隐患。建议仅显式传 state_file 时才 save。

**N-M3 `format_tax_line` None 崩溃**（runner.py:725）：探针记录全被拒时 `attack_accuracy=None`，无基线分支直接 `None*100` → TypeError（实测复现）。健壮模型全拒绝场景真实存在。建议判 None 输出"全部拒绝，无有效作答"。

**N-M4 runner.py:601 `final_fit` 仍是裸调用无 try**：M-30 只堵了 hdb 优雅早退一条路径；final_fit 内部异常（M-33 空方法 PCA 崩溃、embedding 服务挂掉）仍会在攻击跑完、API 成本已花之后炸掉整个 run。建议 try 降级为"跳过聚类"。

**N-M5 stale_report 误判**（dashboard_api.py:361-372）：用 mtime 差判定，切到任何历史批次恒报"看旧了"，与数据是否为空无关；旧批次报告被重写时最新批次反被误判。建议改为与"最新批次名"比较。

**N-M6 切换批次后对比面板不重渲染**（app.js:297-301 vs :138）：runSelect change 只更新 lastOverview，对比表"当前"列停留旧批次，与页面上方总览矛盾。

## 三、结论

本轮修复质量整体很高：**原 43 个分级条目中 33 个完全修复、7 个部分修复、3 个未修**，多处做了双保险和配套修复（S-2 双保险、S-6 连指纹归一化一起修、M-27 三方对齐），测试从"18 绿 1 红 1 崩"提升到 21 全绿，S-1 的统计概念错误已正确根除。

但修复本身带入了 **2 个新的严重问题**，且都是同一模式——**多模型隔离的修补修了一处漏一处**：看板新加的目标选择根本没接线（N-S1），evaluator 的新稳定结果路径没有模型维度、比修复前更危险地污染 R（N-S2）。建议下一批优先：

1. N-S1（EvaluateRequest 加 target，一行级）+ N-S2（evaluator 对齐 safe_twin 的 model 字段修法）
2. N-M1/N-M2（evaluator/update_elo_from_results 覆写 state.json，同一根因两处）
3. N-M3（None 崩溃，一行判空）+ N-M4（final_fit 包 try）
4. M-2/M-5/M-6 三个未修的缓存/真相语义问题（需要设计决策，非一行可修）
5. S-1 收尾：ddof=2 + t 分位数校准
