## 1. 现状摸底：架构与数据流全景

### 1.1 双层架构

项目分两个**严格解耦**的子系统，通过 **subprocess + 文件** 交互（绝不互相 import 内部 API）：

- **`llmsec/`** — 核心安全评估库（攻击流水线、Elo 评分、聚类）。是被调度的"工人"。
- **`control/`** — 元控制层（"代码外面"），通过 subprocess 调用 `llmsec` 的 CLI，只读取公开产物文件。

隔离边界声明见 `control/__init__.py`；MCP 路径明确声明不经三省制（`llmsec/mcp/server.py:13`）。

### 1.2 数据存储方式

**完全基于文件系统**，三种格式：JSON / JSONL / 二进制 pickle(joblib)。**无任何数据库**（`grep sqlite` 全空）。

统一 I/O 层在 `llmsec/core/io.py`：
- `read_json` / `write_json`（原子写 `.tmp → os.replace`，支持 `backup=True` 写 `.bak`）— `io.py:119`, `io.py:158`
- `read_jsonl` / `write_jsonl` / `append_jsonl` — `io.py:46`, `io.py:71`, `io.py:96`
- `load_artifact` / `save_artifact`（joblib 二进制，tmp 名加 `pid.threading.ident` 后缀防并发）— `io.py:209`, `io.py:228`

### 1.3 "唯一真相 + 派生缓存"设计哲学

这是整个数据架构的基石（`llmsec/core/results.py:1-27`）：

> 结果矩阵 R[record][model] → 结果记录 是整个评估体系的**唯一真相**。Elo、预测器、收敛判定都是从 R + 单位特征 X **派生**出来的缓存，可随时从 R 全量重算。

- R 矩阵：`output/state/results.json`，`ResultsMatrix.save()` 写，跨进程文件锁保护（`results.py:84`）。
- Elo 派生缓存：`output/state/elo_cache.json`（可删重建）。
- 预测器派生缓存：`output/predictors/*.pkl`（可重训重建）。

**核心 R 矩阵当前规模**：98 records × 3 models，169 observations，文件 37KB（`_SCHEMA_VERSION = 2`，`results.py:41`）。

## 2. 缓存与生命周期：第一个临界点 ✅ 已整改

> **整改状态**：死缓存已清理（output 373MB→87MB）+ `predictors_legacy` 清理类别 + `embedding_cache` 纳入 `feature_cluster` + `gc_merged_workspaces` 延迟 GC。以下为整改前的现状诊断。

> **核心论断**：数据管理是"全手动、只增不减"模型。`predictors/` 292MB 中 97% 是版本迁移死缓存，merged workspace 不自动删，散落缓存脱离类别管理，唯一清理入口只支持整类软删，无任何自动触发钩子。

### 2.1 predictors/ 死缓存爆炸（实测核心发现）

#### 2.1.1 总量

| 指标 | 实测值 |
|------|--------|
| 总文件数 | **603 个 `.pkl`** |
| 总大小 | **292 MB** |
| 不同大小值 | 仅 277 种（603 文件只有 277 种 size → 大量同尺寸拷贝） |
| size 分布 | <10KB: 113 / 100KB–1MB: 304 / >1MB: 164；最大 1,458,102 B |

#### 2.1.2 版本裂痕（致命发现）

cache_key 格式（`llmsec/evaluation/predictors/blend.py:352`）：
```
f"blend_v2_{r_fp[:12]}_{cat_fp[:8]}_{feat_fp[:8]}_{probe_fp}"
```

版本盐 `blend_v2_` 是 H-11/M-37 修复时引入的（`blend.py:327-328, 350-351` 注释）：`EloPredictorModel` 新增 `no_signal` 属性后，旧 pkl 反序列化会 `AttributeError`，故加版本盐让旧缓存"静默 miss 重训"。

**但旧文件从未被清理**。实测目录里两种前缀并存：

| 前缀 | 文件数 | 体积 | 状态 |
|------|--------|------|------|
| 旧版 `blend_{...}.pkl`（无 v2） | **465** | **283 MB** | **死缓存**——现行代码只生成 `blend_v2_`，永不命中 |
| 新版 `blend_v2_*` | **138** | **7.3 MB** | 真正"活的"缓存 |

> **即 predictors 目录 97.4% 的体积（283/292 MB）是版本迁移遗留的死文件，无自动清理、无淘汰策略，只能靠用户手动 `cache clean predictors` 软删除。**

#### 2.1.3 参数化展开放大

`feat_fp8` 高度集中：单个指纹 `8f691892` 就对应 **212 文件 / 199 MB**。这说明大量预测器共享同一组特征结构（embedding 块维度相同），仅 R 内容或方法清单不同 → cache_key 四因子（`blend.py:321-349`：R 内容 + 方法清单 + features 结构 + 探针指纹）中任一变化即生成新文件。这是设计内的参数化展开，不是 bug，但放大了体积。

旧版 distinct `r_fp12` = 146 个，新版 = 58 个。热门 R 前缀如 `blend_080b3dd93a7f` ×40 文件——同一 R 快照被不同 (cat, feat, probe) 组合展开成几十个文件。

#### 2.1.4 匹配方式：精确名，无 glob

`load_or_fit_blend_predictor`（`blend.py:388-408`）：
- `:396-397`：`key = cache_key(...)` → `cache_path = PREDICTORS_DIR / f"{key}.pkl"` —— **精确文件名拼接**。
- `:399`：`BlendPredictor.load(cache_path)` —— 直接 load 单文件，无目录扫描。

**所以死缓存不是性能问题（每次匹配 O(1)），而是纯体积问题**——`cache list`/`clean` 时才 glob 603 文件（`caches.py:67-70`），非常态路径。

### 2.2 caches.py 的清理能力实为"整类手动软删"

#### 2.2.1 支持的类别（`llmsec/management/caches.py:40-64`，`CACHE_CATEGORIES`）

| 类别 | 路径 | 清理逻辑 |
|------|------|----------|
| `elo_cache` | 单文件 `ELO_CACHE_FILE` | 删单文件 |
| `predictors` | `glob("*.pkl")` 全列 | **glob 全删** |
| `feature_cluster` | `feature_cache.pkl` + `cluster_result.pkl` | 删两固定文件 |
| `task_logs` | `*.log` + `*.progress.jsonl` | **glob 全删** |

#### 2.2.2 零细粒度淘汰

`grep lru|max_age|max_size|evict|expire|ttl|prune|gc` 在 `llmsec/management/`、`control/core/` 内**零命中**任何淘汰策略。`caches.py` 只支持"整类全删"，没有按时间/大小/访问频率的细粒度淘汰。

#### 2.2.3 零自动触发

**不存在任何自动清理触发点**：
- `plan_clean`/`execute_clean`/`cmd_clean` 仅被**显式人工/agent** 入口调用：
  - CLI：`llmsec/management/__main__.py:120`
  - MCP：`llmsec/mcp/tools/actions.py:116,142`（两步确认）
  - 控制层：`control/core/invoker.py:135-139`（经门下省确认）
- `grep on_close|after_run|post_run|teardown|atexit|scheduler|cron|periodic` 在 `llmsec/pipeline/`、runner 相关代码**零命中**。runner 的 `finally` 块只做资源关闭。

**结论：缓存是"只增不减"的累积模型，除非用户/agent 主动喊一声 clean。**

### 2.3 merged workspace 不自动删除

`control/core/workspace.py`：
- `mark_merged(name, target)`（`:143-159`）：**只把 `merged=True`/`merged_at`/`merged_to` 写进 `_index.json`，从不删目录**。注释（`:146`）明说"merge 本身已成功不可逆"。
- `delete_workspace(name)`（`:162-174`）：才是真正 `shutil.rmtree`（`:169`）。

**两者解耦**：merge 后 workspace 永远留在磁盘上（仅打标记），必须再单独调 `delete_workspace` 才释放空间。

**实测断裂点**：`capabilities.py:133` 的 merge capability 调完 `mark_merged` 后**没有链式调 `delete_workspace`** → merged workspace 是隐性累积源。当前 `output/workspaces/_index.json` 只有 1 个未 merge 的 `test_exp`，但一旦跑真实 merge 流程，每个 merged workspace 都会沉淀。

## 3. 查询性能：全量扫描与零索引 ✅ 已整改

> **整改状态**：`elo_tracker_for` 进程内 tracker 缓存（MCP Elo 工具不再每次全量 derive）+ `_discover_runs_cached`（首屏 4 扫→1 扫）+ `/api/attack-sets` 行数缓存 + `/api/runs` 分页 + search_history AND 语义/相关性排序/文本缓存。以下为整改前的现状诊断。

> **核心论断**：全项目零分页、零倒排索引、零查询层缓存（除一处聚类投影缓存）。`search_history` 是子串匹配 + N+1 全文读；`discover_runs` 有两份重复实现且 dashboard 单首屏触发 3 次全目录树扫描；`elo_cache` 对 MCP 路径完全失效。

### 3.1 search_history：子串匹配 + N+1 全文读

**实现位置**：`control/agent/zhongshu/dialogue.py:59-101`（`_do_search_history`）。

执行流程是**两段式 N+1 全读**，零缓存：

1. `:68` `gazette.list_gazettes(recent=50)`：取最近 50 个文牍。
   - `list_gazettes`（`gazette.py:239`）调 `_store.load()`（`store.py:55`）—— **每次 `read_text` 整个 `_index.json` 再 `json.loads`，无缓存**，然后内存排序切前 50。
   - 注意：`_index.json` 是**全量读**所有项只为切前 50。
2. `:69` 对每个文牍 `gazette.read_events(plan_id)`：`gazette.py:145-165` 把**整个 `.jsonl` 一次性 `read_text` 进内存**（`:151`），逐行 `json.loads`。

**匹配逻辑**（`:83`）：`if any(kw in searchable for kw in keywords)` —— **纯子串匹配**，无分词、无 TF-IDF、无倒排、无正则。

**实测当前规模**：`output/gazette/` 14 个 jsonl / 66 事件行 / ~19KB；`_index.json` 3.3KB / 10 plan 项。当前每次 search 最坏读 ~22KB，无压力。

**放大预测**：
- **500 文牍**：`_index.json` ~165KB（全量读只为切前 50）+ 50 次 jsonl 读 ≈ 70KB → **~50–100 ms/次**（主要是 50 次 syscall + JSON parse）。
- **1000 文牍**：`_index.json` ~330KB（parse 开始显现）→ **~100–150 ms/次**。
- N+1 的线性放大点在"`_index.json` 全量读 + 50 个候选 jsonl 全文读才能做子串匹配"——**没有 token 倒排意味着任何"找含 X 的历史"都必须把候选全文加载**。

## 4. 并发与一致性：文件锁的边界 ✅ 已整改（核心项）

> **整改状态**：`_file_lock` 加 strict 参数——save/merge/runs 用 `strict=True`（超时抛 LockTimeout），publish_tracker 维持放行不中断评估；`AtomicIndexStore.update` 加跨进程文件锁（`control/core/locks.py`）。§4.2 两套 TASKS dict 和 §4.5 snapshot 裸读属低优先级，未动。以下为整改前的现状诊断。

> **核心论断**：`results.json` 文件锁超时后**静默放行**，调用方零感知，RMW 临界区被打破时**静默丢观测**；两套无锁 TASKS dict 靠 GIL 兜底；`AtomicIndexStore` 仅进程内锁，`_index.json` RMW 无跨进程保护。

### 4.1 results.json 锁超时静默放行（最危险）

`_file_lock`（`results.py:84-133`）超时策略（`:111-118`）：
```python
if not acquired:
    # #15：超时放行时必须留痕
    logger.error("results.json 文件锁获取超时(%.0fs)，放行写入...", timeout, filepath)
yield  # ← 拿到锁（或超时放行）后执行临界区
```

**三个致命特征**：
1. **超时只 `logger.error`，不抛异常，不返回状态**。
2. **调用方零感知**：`with _file_lock(...)` 无 `as`，4 个调用点（`results.py:332` save、`elo_access.py:149` publish_tracker、`merge.py:131` execute_merge、`runs.py:271` 删 R 列）没有任何一个检查"是否真拿到锁"。
3. **丢更新不触发损坏检测**：`load()`（`results.py:336-364`）有 `.bak` 恢复 + `.corrupt.bak` 取证，但两个完整 JSON 互相覆盖读到的是**合法 JSON 只是少了数据**——**静默丢失观测**。

这正是 `elo_access.py:146-148` 注释自承的 H5/H6 场景：
> H5/H6 修复：整段 load→modify→save 纳入文件锁，防并发 publish 丢更新（TOCTOU）。

**但这个修复只在"能拿到锁"时有效**。超时放行后两个 RMW 临界区交叉 → 后写覆盖先写 → 先写者 upsert 的观测全部丢失。注释 `:112-113` 自己也承认："对'唯一真相'存储，静默交替写会损坏且无信号"。

**锁粒度局限**：基于 1 字节的 `msvcrt.locking`/`fcntl.flock`，进程级有效，**同进程不互斥**（flock 对同进程同 inode 是附加而非互斥）——这是 `save(_locked=True)` 路径存在的根因（`results.py:329`）。

### 5.3 bus 消息总线局限

`control/agent/bus.py:78-129` MessageBus：

**门下省未订阅时 STEP_START 静默丢失**（最危险的断裂点）：

门下省订阅在 `init_menxia()`（`listener.py:63-82`）调用时才生效（`bus.subscribe(MENXIA, [KIND_STEP_START], _on_step_start)` `:79`）。

executor 的封驳检测**不依赖订阅者在线**——它走主动轮询 bus.recent（`executor.py:191-201`）：
```python
def _check_block_for_step(plan_id, step_id):
    recent = bus.recent(since_ts=time.time() - 5.0)   # ← 查近 5 秒消息
    for m in reversed(recent):
        if (m.kind == "block" and m.plan_id == plan_id
                and m.payload.get("step_id") == step_id):
            return m.payload.get("ticket")
    return None
```

**但这有前提**：`notify` 是同步的（bus.py:91）。若门下省**已订阅**，`_on_step_start` 在 `notify` 返回前就执行完，发 `KIND_BLOCK`，executor 紧接着查 recent（5s 内）能查到。

**若门下省未订阅**（init_menxia 没调/失败/进程刚启动 router 还没加载）：
- `_on_step_start` 永不执行，没有 `KIND_BLOCK` 消息。
- `_check_block_for_step` 返回 None → **critical 步骤直接放行执行**。

> **封驳机制强依赖门下省在 `bus.publish` 同步链路内完成审查**。一旦门下省未初始化、或审查逻辑慢于 5 秒，critical 步骤会无封驳直接执行。bus 无持久化 + 无重投递 + 5s 轮询窗口 = 封驳可被静默绕过。

- **无 reaper/无 orphan 扫描**：`task_manager.py` 没有子进程 reaper，没有启动时扫 orphan 的逻辑。

### 5.5 env_snapshot 与 param_overrides 叠加的隐式优先级

`run_evaluation` 的叠加逻辑（`llmsec/mcp/tools/tasks.py:152-169`）：
- 先 env_snapshot 的全部 key（`:153-158`），再 param_overrides 转成 `LLMSEC_PARAM_<NAME>` 覆盖（`:165-169`）。
- **隐式优先级**：param_overrides 后写覆盖 env_snapshot 同名 key（dict.update 语义）。docstring（`tasks.py:116-118`）未声明此优先级。
- **语义不对称**：`orchestrate_runs` 走完全不同的路径（`:340-354` 构造 `python -c` 脚本，在脚本里直接改 `os.environ`），**不走 env_snapshot 机制，也无 env_override 叠加**。

## 6. 架构根因分析

### 6.1 把"JSON 文件 + 文件锁"当数据库用

项目的数据管理本质是：**用文件系统模拟数据库**。
- **原子写 `.tmp → os.replace`** 模拟单次写事务的原子性。
- **跨进程文件锁 + RMW** 模拟读-改-写事务。
- **`.bak` 轮转 + `.corrupt.bak` 取证** 模拟崩溃恢复。
- **指纹缓存（cache_key）** 模拟索引键。
- **`_index.json`** 模拟元信息索引。

### 6.2 四个结构性缺失

| 缺失 | 现状 | 后果 |
|------|------|------|
| **查询索引** | 全靠 glob + 全量读 | search_history/list_runs 放大后卡顿 |
| **真事务** | 靠文件锁 + RMW 模拟，超时即放行 | 静默丢观测 |
| **生命周期管理** | 靠手动 CLI clean | 只增不减，死缓存累积 |
| **并发扩展性** | 单文件锁串行化所有写 | 高并发下锁瓶颈 |

### 6.3 适用边界

这套方案在**单机、低并发、中小数据量**下是**精巧且可靠的**——代码质量很高，防御极充分。遍布 `M##/P##/F##/H##/R##/S##/B##` 系列的修复注释（无传统 TODO/FIXME，全是"已修复"标记）揭示了一段与并发损坏、Windows 兼容性、JSON 边界 case 反复搏斗的历史。

**代表性血泪**：
- **F-3/F1**（`results.py:314, 338`）：权威存储崩溃/并发导致静默数据丢失 → 原子写+备份兜底。
- **H5/H6**（`elo_access.py:146`）：并发 publish 的 TOCTOU 竞争 → 整段 RMW 纳入文件锁。
- **P9**（`io.py:243-256`）：并发写同一 cache key 时两线程共用 `.tmp` 互相截断 → tmp 名加 pid.tid 后缀。
- **M12**（`io.py:174`）：NaN/Infinity 写出非法 JSON → `allow_nan=False`。
- **M9**（`safe_twin.py:184`）：`append_jsonl` 无锁并发 append 产生半写行 → 加 `_TWIN_APPEND_LOCK`。

**边界之外即力不从心**：当评估规模从"几十模型几百方法"进入"上百模型上千方法 + 长期积累的历史 run"时，这套文件系统方案会全面承压。

## 8. 演进方向建议（战略级，含已落地情况）

> 以下为调研时的候选方向。标注 ✅ 已落地 / ❌ 不做 / ⟳ 待论证。每项保留原始的成本/收益/风险评估作为决策记录。

### 8.1 缓存与生命周期（最紧迫）✅ 已落地

**选项 A：即时清理死缓存 ✅**
- 跑一次 `llmsec-manage caches clean predictors_legacy --yes` 清掉 283MB 死缓存。
- 成本：极低。收益：立刻回收 97% predictors 体积。风险：零。**已执行，output 373MB→87MB。**

**选项 B：cache_key 版本迁移时自动清理旧前缀 ✅**
- `caches.py` 新增 `predictors_legacy` 类别（`_is_legacy_predictor` 按 `_LIVE_PREDICTOR_PREFIXES` 判定）。
- 成本：低。收益：未来 `blend_v3` 时有现成清理入口。**已实现。**

**选项 C：LRU 淘汰 + 容量上限 ⟳ 待论证**
- `load_or_fit` 记录访问时间，predictors 目录达阈值时淘汰最久未访问。
- 成本：中。收益：自动控制体积。风险：淘汰活的缓存会导致重训。**当前规模不需要，待 predictors 数达数百时再议。**

**选项 D：merged workspace 自动 GC ✅**
- `gc_merged_workspaces(older_than_days)` 延迟清理（按 merged_at 超期），保留 gc_log 审计链。
- 成本：低。收益：消除隐性累积。**已实现（CLI `workspace gc` + MCP 工具）。**

**选项 E：散落缓存纳入类别管理 ✅**
- `embedding_cache.pkl` 纳入 `feature_cluster` 类别。
- 成本：低。收益：清理命令覆盖全部派生缓存。**已实现。**

### 8.2 查询性能 ✅ 已落地

**选项 A：runs 索引层 ✅**
- `_discover_runs_cached()` 按 `(runs_dir mtime, batch 目录数)` 签名做进程内缓存。首屏 4 扫→1 扫。
- 成本：中。收益：dashboard 首屏从 4 次全扫降到 1 次。**已实现。**

**选项 B：elo_cache 覆盖 MCP 路径 ✅**
- `elo_tracker_for(model)` 进程内 tracker memoize（按列指纹失效）。同 MCP 会话连续调用只 derive 一次。
- 成本：低。收益：MCP Elo 工具不再每次全量重算。**已实现（采用进程内 tracker 缓存而非 from_dict 重建，更安全）。**

**选项 C：search_history 倒排索引 ⟳ 待论证（部分已用更轻量方案解决）**
- 调研后结论：当前数据天然小（9 plan，57 字符/plan），首要问题是召回质量而非速度。
- **已落地**：AND 语义 + 相关性排序（intent×3/user_text×2/steps×1）+ 文本源补全（step_started.description + commission user_text）+ 进程内文本缓存（100 次搜索 4.2ms）。
- **2-gram 倒排暂不引入**：缓存层已让搜索成本趋近于零，索引在此规模无感知收益。

**选项 D：dashboard 路由分页 ✅**
- `/api/runs` 加可选 `limit/offset`（默认全量，向后兼容）+ `_paginate` helper。
- 成本：低。收益：前端可按需加载。**已实现。**

**选项 E：`/api/attack-sets` 缓存行数 ✅**
- `_ATTACK_SET_CACHE` 按文件 mtime+size 签名缓存行数。
- 成本：低。收益：消除每次全量读 37MB。**已实现。**

### 8.3 并发与一致性 ✅ 核心已落地

**选项 A：results.json 锁超时改为失败重试而非放行 ✅**
- `_file_lock` 加 `strict` 参数：save/merge/runs 用 `strict=True`（超时抛 LockTimeout），publish_tracker 维持 `strict=False`（放行不中断评估）。
- 成本：低。收益：消除权威写的静默丢观测。**已实现。**

**选项 B：results.json 迁移 SQLite（WAL 模式）⟳ 待论证（长期档 A）**
- R 矩阵改存 SQLite，利用 WAL 事务 + 索引。
- 成本：高（改 `ResultsMatrix` 全部 I/O + 派生层适配）。收益：真事务 + 查询索引 + 并发。风险：大改核心存储，需充分迁移测试。**当前规模（98 records）远未到瓶颈，待数据量增长触发阈值时再单独立项。**

**选项 C：保留 JSON 但补跨进程锁语义 ✅**
- `AtomicIndexStore.update` 加跨进程文件锁（`control/core/locks.py`，基于 filelock 包）。
- 成本：中。收益：消除索引 RMW 丢更新。**已实现。**

**选项 D：合并两套 TASKS dict ⟳ 待论证**
- `task_manager.py:33` 和 `routers/tasks.py:30` 统一为一个。
- 成本：中。**低优先级，待长期档。**

### 8.4 状态传递与上下文 ✅ 部分落地

**选项 A：关键内存态落盘 ⟳ 待论证**
- task 注册表落盘，重启时重建。
- 成本：中。**待长期档。**

**选项 B：统一 task 语义跨进程可见 ❌ 不做**
- **经评估决定不做**：三个服务对象不同——前端用户知道自己在干嘛；三省制面向不知道怎么操作的高级功能；MCP 计划后续开放远程服务（用户连项目都没装，不可能与前端互动）。两方/三方没有必要互通。

**选项 C：bus 持久化 + 重投递 ⟳ 待论证**
- 关键消息落盘，订阅者重启后补全。
- 成本：中高。**待长期档。**

**选项 D：task_manager 启动扫 orphan ⟳ 待论证**
- 重启时扫描无 task_id 关联的 run 目录。
- 成本：中。**待长期档。**

**选项 E：env_snapshot 与 param_overrides 语义统一 ✅**
- `orchestrate_runs` 加 `env_snapshot` 参数，base_env 合并进每条 spec 的 env_override，与 run_evaluation 语义一致。
- 成本：低。收益：消除两条路径的语义不对称。**已实现。**
